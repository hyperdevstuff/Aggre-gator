    Orientation briefing · for someone who has never opened this repo

    A bookmark manager whose real product is the published collection.

    Saving one link is cheap. A good, maintained, ordered set of links is expensive. So the product is “collect once, share the whole thing” — the owner pays, and every viewer gets a polished public page without signing up. The private half is finished. The social and monetization half is the entire remaining job.

    04

    The data model, and why phase 2 was the gate

    Eleven tables. The pivotal change is that a bookmark no longer lives in exactly one collection — which is what made “save someone else’s link” even expressible.

    

  
    
    
    
      
    Why the migration order was weird
    
      
    
        It shipped as schema+backfill → dual-read → archived_at → drop, not
        (a)(b)(c)(d). Dropping collectionId before archiving moved off the
        “Archived” collection would have forced a throwaway “archive-via-membership” implementation
        that step (d) then deletes. Doing (d) first made the drop a pure storage change with no dead code.
      
    
    
    
    
    
      
    Blast radius
    
      
    
        collectionId was referenced 64 times across 16 files (38 backend bookmarks,
        15 backend collections, 11 share, 50 frontend). The roadmap calls it “the widest-reaching edit”.
        Sequencing it so the app is never broken mid-migration is the whole difficulty.
      
    
    
    
  
    

  
    
    adr-001Why the links table is deferred to phase 5›
    
    
      
    A links table keyed by normalized URL would give everyone one shared preview and one
      “saved 1.2k times” count. It was deliberately not built in phase 2, and the reasoning is the
      best-written part of this repo.
    
      
    A unique url_key forces URL normalization to be correct immediately. Getting it
      wrong is not cosmetic — it merges two genuinely different pages into one row, and two users save
      one URL believing they saved two. That is data loss the user cannot undo.
    
      
    The conclusion from Pinterest’s own engineering note is humbling: you cannot do it with a static
      allowlist, and the safe direction to be wrong in is “keep the parameter” — over-stripping silently
      merges content, under-stripping merely leaves a duplicate.
    
      
    
        
    Phase 5 shape
    Write normalizeUrl() pure and unit-tested → index url_key but don’t make it unique → use it for soft “you may already have this” prompts → promote to unique only when save-someone-else’s-link ships.
    
        
    Never
    Lowercase the path, or strip www. Both are load-bearing on real sites. Storing the normalized URL for navigation is also wrong — always store and link the original.

    Why MARATHON exists at all
    
    
    Two agents — one backend, one frontend — work
    in parallel on the same repo. Without ownership rules they collide on things that do not merge cleanly:
    
    
    
      
    
        
    CollisionRule
    
        
          
    Two agents both generating 0012_*Only agg-be writes migrations. This is “the single most likely merge conflict”.
    
          
    Both want to mark TASKS.md doneBackend owns it during work; frontend updates once at the end of its branch.
    
          
    Root package.json / bun.lockRead-only for both. A dependency bump lands as its own PR to main first, then both branches rebase.
    
          
    ADR numbersAssigned to the backend. “Renumber before committing rather than after” — they are the only thing here that can collide silently.
    
          
    Merging worktree → worktreeNever. Only feat/* → main.
    
            
      
    
    
    
  
    

  
    
    
    
      
    Contract-first
    
      
    The frontend needs endpoints that do not exist —
      analytics (be-16), plan enforcement (be-19), checkout (be-21),
      verification status (be-06). So the backend publishes the response shape plus the
      TypeScript types early and the frontend builds against mocks. Otherwise the frontend stalls for a week.
    
    
    
    
    
      
    Definition of done, every issue
    
      
    typecheck + lint + test
      pass, TASKS.md updated to match reality, any new API surface has an integration test,
      and a PR to main is opened — you do not merge main yourself. “Every wave ends green.”
    
    
    
  
    

  
    The waves
    
  
    Waves are dependency-ordered batches of backend issues.
  You do not skip ahead because a later one is more fun — each wave assumes the one before it. (Waves are a
  backend concept; the frontend has two Steps.)
